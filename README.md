# Блок 8. RAG-помощник по базе знаний Handbook

Консольное приложение задаёт вопросы по учебной базе знаний
`D:\study\handbook`: находит подтверждающий документ и отвечает точными
цитатами с указанием источника. Если подтверждения нет, помощник честно
сообщает об этом и не выдумывает факт.

Единственный источник данных — папка `handbook`. Экзаменационный
игрушечный корпус `D01`–`D16` больше не используется.

## 1. Цель проекта

Показать поисковую часть RAG без обучения большой языковой модели:

1. собрать текстовый корпус из markdown и Word-документов;
2. удалить дубли и служебные файлы;
3. разбить документы на чанки;
4. построить TF-IDF индекс;
5. найти ближайшие фрагменты по вопросу;
6. выдать точные предложения-цитаты с указанием источника;
7. сравнить настройки поиска по Top-1 и Hit@K;
8. проверить случай, когда ответа в документах нет.

## 2. Источник данных

Источник: `D:\study\handbook`. Путь можно переопределить переменной
окружения `HANDBOOK_DIR`.

Корпус:

- **77 документов**: 20 markdown-файлов и 57 Word-документов;
- **~167 тыс. слов**;
- тематические конспекты `01-python.md` … `11-karta-istochnikov.md`;
- `konspekty/*.md` — конспекты ноутбуков;
- `istochniki/**/*.docx` — исходные Word-документы по блокам.

Сборка:

```bash
python main.py --build-corpus
```

Что делает сборщик:

- извлекает текст из `.md` и `.docx`;
- удаляет точные дубли по SHA1 нормализованного текста;
- исключает служебные и потенциально чувствительные файлы (экспорт
  чата, доступы, личные заметки);
- сохраняет метаданные: путь, блок, тип, язык, число слов;
- не включает PDF, изображения, архивы и сырые данные.

Результат: `data/handbook_documents.json` и статистика
`reports/handbook_corpus_stats.json`. Полный текст корпуса не
коммитится в Git: он собирается локально.

Схема данных: [docs/data_description.md](docs/data_description.md).

## 3. Параметры

| Параметр | Значение |
|---|---:|
| `CHUNK_SIZE` | **600** |
| `OVERLAP` | **100** |
| `SEARCH_METHOD` | **`char_wb`** |
| `TOP_K` | **3** |

При этих настройках получилось **2583 чанка**. На 50 контрольных
вопросах базовый вариант дал **Top-1 = 0.720** и **Hit@K = 1.000**.

## 4. Пять экспериментов

| Код | Чанк | Overlap | Поиск | Top-K | Чанков | Top-1 | Hit@K |
|---|---:|---:|---|---:|---:|---:|---:|
| A: слова / 1 источник | 380 | 45 | word | 1 | 3883 | 0.640 | 0.640 |
| B: буквы / 2 источника | 380 | 45 | char_wb | 2 | 3883 | 0.760 | 0.920 |
| C: короткие чанки | 200 | 30 | char_wb | 3 | 7855 | 0.680 | 0.940 |
| D: длинные чанки | 700 | 100 | char_wb | 3 | 2154 | **0.780** | 0.980 |
| E: слова / без перекрытия / 5 источников | 300 | 0 | word | 5 | 4286 | 0.680 | **0.980** |

### Объяснение по графикам и таблице

- **A против B.** При одинаковых чанках поиск по группам букв
  (`char_wb`) дал Top-1 0.760 против 0.640 у поиска по словам. Разные
  окончания русских слов меньше мешают.
- **B против A по Top-K.** У B `top_k=2`, поэтому Hit@K = 0.920: даже
  если верный документ не первый, он попадает в выдачу.
- **C против D.** Длинные чанки (700) дали Top-1 0.780, короткие (200) —
  0.680. Вопросы часто требуют контекста целого раздела, поэтому
  длинный чанк выигрывает, хотя короткий точнее нацелен на предложение.
- **Новый опыт E.** Здесь изменены сразу три вещи: поиск по словам,
  `overlap=0`, `top_k=5`. Top-1 = 0.680, Hit@K = 0.980. Большое Top-K
  повышает шанс найти верный источник, но добавляет шум; отсутствие
  перекрытия уменьшает число чанков, но может разорвать мысль на
  границе. Word-поиск слабее `char_wb` на русских словоформах.

Графики: `reports/handbook/charts/experiments_metrics.png` (Top-1 и
Hit@K) и `reports/handbook/charts/chunks_per_experiment.png`
(число чанков).

## 5. Контрольный вопрос и вопрос без ответа

**Контрольный вопрос:** «Почему для KMeans обязательно масштабирование
признаков?»

Первый источник — `istochniki/08-ml/Block07_Clustering_VSCode_Guide`.
Ответ:

> Поэтому для KMeans числовые признаки обязательно масштабируются
> через StandardScaler.

Файл: `reports/handbook/custom_answer.txt`.

**Посторонний вопрос:** «Сколько студенту нужно отжаться на брусьях?»

Лучший найденный фрагмент имел сходство 0.195. При пороге 0.20 система
ответила:

> Не нашёл подтверждённого ответа в учебных документах.

Файл: `reports/handbook/no_answer.txt`. Это важное правило
ответственного ИИ: лучше признать отсутствие данных, чем выдать
случайный фрагмент за ответ.

## 6. TF-IDF, нейросетевой поиск и полноценный RAG с LLM

| Подход | Что делает | Глубокое обучение | Ограничение |
|---|---|---|---|
| **TF-IDF** | Считает статистическую важность слов / групп символов и сравнивает векторы | Нет | Не понимает синонимы без общих слов |
| **Семантический поиск** | Сравнивает эмбеддинги предобученной нейросети | Да, готовая модель | Требует ресурсов и тоже ошибается |
| **RAG с LLM** | Поиск + передача фрагментов языковой модели, которая пишет новый ответ | Да | LLM может галлюцинировать; нужна проверка по источникам |

Наш помощник реализует **Retrieval** и показывает точные выдержки из
источников. Пока не подключена языковая модель, это **не генерация**.
В факультативных режимах можно:

- `--neural` — сравнить нейросетевой поиск `sentence-transformers`
  с TF-IDF;
- `--llm` — сгенерировать ответ локальной моделью `Qwen2.5-0.5B-Instruct`
  и проверить, не придумала ли она факты.

Оба режима требуют интернета и установки дополнительных пакетов; на
обычном запуске они выключены, чтобы обязательная часть работала без сети.

## 7. Архитектура

| Модуль | Назначение |
|---|---|
| `src/config.py` | пути, параметры, пороги, пять экспериментов |
| `src/corpus_builder.py` | сборка корпуса Handbook из md/docx, дедуп и метаданные |
| `src/data_loader.py` | загрузка JSON и сохранение CSV/JSON/TXT |
| `src/chunker.py` | разбиение документов на чанки с перекрытием |
| `src/retriever.py` | TF-IDF индекс и поиск разных документов |
| `src/answerer.py` | ответ цитатами с источниками и отказ при слабом сходстве |
| `src/evaluator.py` | Top-1 и Hit@K, поддержка нескольких правильных источников |
| `src/experiments.py` | перебор настроек и сбор таблицы результатов |
| `src/assistant.py` | высокоуровневый помощник для консоли |
| `src/pipeline.py` | общий сценарий поиска, экспериментов и отчётов |
| `src/visualizer.py` | сохранение графиков |
| `src/report_builder.py` | итоговый markdown-отчёт |
| `src/neural_retriever.py` | факультативный семантический поиск |
| `src/llm_generator.py` | факультативная генерация локальной LLM |
| `main.py` | единый сценарий запуска |

## 8. Как запустить

```bash
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt

python main.py --build-corpus
python main.py
python -m pytest -q
```

Режимы приложения:

```bash
python main.py --ask
python main.py --question "Что такое переобучение?"
python main.py --neural
python main.py --llm
```

После полного запуска появляются:

- `reports/handbook/experiments.csv` — таблица пяти опытов;
- `reports/handbook/retrieval_check.csv` — проверка каждого вопроса;
- `reports/handbook/settings.json` — параметры запуска;
- `reports/handbook/demo_answer.txt` — демонстрационный ответ;
- `reports/handbook/custom_answer.txt` — контрольный ответ;
- `reports/handbook/no_answer.txt` — пример без ответа;
- `reports/handbook/charts/*.png` — графики;
- `reports/handbook/final_report.md` — итоговый отчёт;
- `reports/handbook_corpus_stats.json` — статистика сборки корпуса;
- `notebooks/Block08_RAG_Handbook_SOLVED.ipynb` — разведочный ноутбук.

## 9. Ограничения и приватность

- корпус собран автоматически из md/docx, без PDF и OCR;
- в Handbook много пересекающихся конспектов и первоисточников;
- TF-IDF не понимает синонимы без общих слов;
- ответ собирается из цитат, а не генерируется LLM;
- порог сходства нужно настраивать на своих вопросах;
- найденная цитата не заменяет проверку прав доступа и содержания;
- семантический поиск и LLM — факультатив и требуют ресурсов;
- полный текст корпуса не публикуется: его нужно собирать локально и
  проверять на наличие персональных данных.
